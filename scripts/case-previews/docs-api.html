接入准备

一、接入准备与鉴权

一、接入准备

第 1 步提交接入申请，提供企业名称、统一社会信用代码与回调域名
第 2 步获取 app_key（形如 MK-2026-0918）与 app_secret（32 位十六进制字符串）
第 3 步在测试环境完成签名自检，调用 GET /categories 验证鉴权是否通过
第 4 步生产环境发布前，将服务器出口 IP 加入白名单（最多 20 个）
第 5 步申请所需权限范围，默认授予 ticket:read，写入类权限须单独申请

二、签名算法

  • 待签字符串 = 请求方法 + 路径 + 时间戳 + 随机串 + 请求体 SHA-256 值，各段以换行符连接。
  • 签名值 = HMAC-SHA256(待签字符串', app_secret)，输出小写十六进制。
  • 时间戳与服务端偏差不得超过 300 秒；随机串 16 位，同一 app_key 下 5 分钟内不得重复。
  • 签名结果放入 X-Signature 请求头，app_secret 不得出现在前端代码或客户端。

三、签名计算示例

待签字符串

POST 换行 /v2/tickets 换行 1789603200 换行 8f2c4a91b7d3e605 换行 4a7f…（请求体 SHA-256 值）

签名值

9d1c77ab4e05f8326c9a1b0d5e3f7412ac86be0955d3f2708ab41c6de92f0357

请求头

X-App-Key: MK-2026-0918；X-Timestamp: 1789603200；X-Nonce: 8f2c4a91b7d3e605；X-Signature: 上述签名值

签名失败返回 401 与错误码 AUTH_1002；连续 20 次签名失败将锁定 app_key 10 分钟。

四、接口详解：创建工单

API-01 POST /tickets

字段类型必填说明
merchant_id字符串是商家标识，18 位
order_id字符串是关联订单号
category_code字符串否问题分类编码，缺省由系统自动分类
title字符串是工单标题，长度 4 至 80 字符

impact_score数值否影响面评分，0 至 100，缺省由系统计算
priority枚举否low / normal / high，缺省 normal

响应示例

成功（201）

code 为 0；data 含 ticket_id（形如 T202609160001）、status 为 pending、created_at 为 2026-09-16T10:24:08+08:00、estimated_timeout_probability 为 0.81

命中优先队列

当 estimated_timeout_probability ≥0.7 时，队列标记为 priority，列表接口按 impact_score 倒序展示

幂等

带 Idempotency-Key 重复提交时返回首次结果，HTTP 状态仍为 201，响应头标记 Idempotent-Replay: true

本接口错误码

  • 400 TICKET_4001 参数缺失或长度越界
  • 403 AUTH_1003 缺少 ticket:write 权限
  • 409 TICKET_4009 24 小时内同订单重复建单
  • 429 RATE_2001 超过 20 QPS 限流

幂等键建议

键值构成建议使用 order_id + 时间戳组合，避免人工重试造成重复建单
创建工单返回 ticket_id 与超时概率，≥0.7 自动进入优先队列第 6 / 10 页

六、回调订阅与重试策略

一、订阅管理

接口说明限制

DELETE /callbacks/{id}删除订阅，立即停止推送删除后不可恢复

二、事件类型

ticket.assigned工单完成分派时推送，含处理人与分派时延
ticket.closed工单归档时推送，含滞留时长与是否超时
ticket.corrected分类被人工纠正时推送，含原标签与新标签
ticket.timeout_warning工单接近 SLA 时推送，提前 10 分钟触发

三、重试时间表

重试次序间隔累计耗时说明
第 1 次1 秒1 秒立即重试
第 2 次5 秒6 秒瞬时故障覆盖
第 3 次30 秒36 秒网络抖动覆盖
第 4 次300 秒5 分 36 秒服务重启覆盖
第 5 次1,800 秒35 分 36 秒最终重试，失败后进入死信
回调要求：接收端须在 3 秒内返回 HTTP 200；同一事件可能重复推送，接收端须按 event_id 去重；死信事件可通过 GET /callbacks/{id}/dead_letters 查询并手动重放。

七、限流、配额与错误码

一、限流与配额

项目默认值提升方式超限表现
默认限流50 QPS提交扩容申请，需说明峰值场景429 与 RATE_2001
写入类限流20 QPS同上，上限 100 QPS429 与 RATE_2001
日调用配额200,000 次申请提升，单次最高 1,000,000 次429 与 QUOTA_3001
批量接口10 QPS，单次 ≤50 条不支持提升429 与 RATE_2002
