## 2. 问题描述

模型先输出思考内容、再输出正文时，正文已经开始出现在主界面，但执行摘要仍持续显示“正在思考”。只有正文流完全结束、最终回答被标记后，界面才切换为“已完成 X 次思考”的最终摘要。

正常情况下，界面应区分两个时间点：

1. **思考段结束：** 次级摘要立即从“正在思考”切换为完成态，正文可以继续流式输出。
2. **整个代理运行结束：** 中间过程折叠为全局执行摘要，最后正文被标记为最终回答。

原实现把第一个时间点推迟到了第二个时间点，导致状态文字与当前可见内容不一致。

## 3. 根因分析

### 3.1 Chat 模式

Chat 流转换器会在第一段正文到达前发送 `reasoning-end`。但 `CoworkView` 收到该事件后只停止耗时计时，没有更新思考消息元数据。

思考消息因此继续保持：

```text
isStreaming: true
isFinal: false
isThinking: true
```

执行状态选择器只要发现符合上述条件的思考消息，就会显示“正在思考”。直到整个响应流结束，原实现才统一完成思考消息和正文消息。

### 3.2 Pi Work 模式

Pi 运行时收到 `thinking_end` 后同样只关闭内部思考标记并停止计时。思考消息要等到整个 assistant `message_end` 才写入完成元数据。

当正文较长时，思考消息会在正文流式输出期间一直处于运行态。停止或错误发生在 `message_end` 之前时，还可能永久保留错误的运行元数据。

### 3.3 持久化快照

Chat 模式会在流式过程中定时保存 SQLite 快照。原快照根据整个会话是否仍在运行来决定思考消息是否流式，而没有区分“会话仍在运行”和“当前思考段已经结束”。

如果应用在正文输出期间退出，重新加载后可能恢复出一个已经结束、却仍标记为流式的思考消息。

## 4. 修复目标

- `reasoning-end` 或 `thinking_end` 到达时立即完成对应思考消息。
- 正文开始流式输出后，次级摘要不再显示“正在思考”。
- 最终回答仍只在整个运行结束后设置 `isFinalAnswer`，不改变中间回答展示规则。
- 正常完成、用户停止、请求取消、运行时错误和缺失结束事件都能完成思考消息。
- 完成操作必须幂等，避免同一思考消息重复更新或累计两次耗时。
- 多段思考可以重新打开状态，并继续累计同一条思考消息的实际耗时。
- 持久化快照准确保存思考消息的独立完成状态。

## 5. 修复方案

### 5.1 渲染端思考生命周期

新增 `ThinkingMessageLifecycle`，集中负责以下行为：

- 启动和累计当前思考段耗时。
- 在思考段结束时清除该消息尚未提交的 RAF 更新。
- 立即派发完整思考内容及完成元数据。
- 记录思考消息是否已经完成，供 SQLite 快照构建使用。
- 对流结束、取消和错误路径提供幂等兜底。
- 后续新思考段开始时重新打开生命周期，并继续累计耗时。

完成后的消息元数据为：

```text
isStreaming: false
isFinal: true
isThinking: true
thinkingDurationMs: 当前累计耗时
```

### 5.2 Chat 新建与继续会话

两个 Chat 路径采用相同状态时序：

```text
reasoning-start
  -> 思考消息进入流式状态

reasoning-delta
  -> 更新思考文本

reasoning-end
  -> 立即完成思考消息
  -> 次级摘要切换为完成态

text-delta
  -> 正文继续流式输出

响应流结束
  -> 正文设置 isFinalAnswer
  -> 中间过程折叠为全局执行摘要
```

取消和错误路径也调用同一个完成操作，因此不会遗留“正在思考”。

### 5.3 Pi Work 生命周期

新增 `PiThinkingLifecycle`，将以下状态从运行时适配器的零散布尔字段中收拢：

- 当前思考段是否打开。
- 当前思考消息是否已经完成。
- 多段思考的累计耗时。

Pi 运行时现在会在以下事件中完成活跃思考：

- `thinking_end`：正常思考段结束。
- `message_end`：供应方未发送独立结束事件时的兜底。
- `agent_end`：整个运行结束前的最后兜底。
- `stopSession`：用户主动停止。
- assistant error：运行时错误结束。

已经完成的思考不会在后续 `message_end` 或 `agent_end` 中重复提交；如果出现新的思考增量，生命周期会重新打开。

### 5.4 最终回答语义保持不变

本次没有提前设置 `isFinalAnswer`。

- 正文流式输出期间仍属于中间可见正文。
- 所有中间正文在最终回答出现前继续保持可见。
- 只有完整代理运行结束时，最后一个有效正文才设置 `isFinalAnswer: true`。
- 最终回答出现后，之前的思考、工具调用和中间回答才统一折叠到全局执行摘要。

因此本次只修复“当前动作状态不准确”，不会破坏此前确定的中间回答与最终回答展示规则。

## 7. 兼容性

- 未新增或修改 IPC 通道。
- 未修改 SQLite 表结构。
- 未修改现有消息元数据字段定义。
- 历史消息可以继续读取。
- OpenClaw 默认 Work 路径不创建该类独立思考消息，因此行为不受影响。
- `Reasoning`、`ChainOfThought` 和执行摘要组件接口保持不变，只接收到更准确的元数据。

## 8. 测试覆盖

新增或扩展以下测试：

- Chat 思考在结束事件到达时立即完成。
- 同一思考生命周期重复完成时保持幂等。
- 后续新思考段可以重新打开并累计耗时。
- Pi 思考段状态和完成状态相互独立。
- Pi 收到 `thinking_end` 后，在 `message_end` 前已经发出完成元数据。
- 用户停止 Pi 会话时完成活跃思考。
- Pi assistant 错误结束时完成活跃思考。
- 最终回答仍只在 `agent_end` 后设置。

本地验证结果：

| 验证项 | 结果 | 说明 |
| --- | --- | --- |
| `npm run build:tsc` | 通过 | TypeScript 编译无错误 |
| `npm run lint` | 通过 | `oxlint src/` 无错误 |
| 相关 Vitest | 通过 | 8 个测试文件、58 项测试全部通过 |
| 全量 Vitest | 环境受限 | 131 个文件、1312 项通过；45 项因 SQLite 原生模块 ABI 和目录写权限失败 |
| `git diff --check` | 通过 | 无冲突标记或空白错误 |

全量测试失败与本次改动无关，集中在：

- `better-sqlite3` 当前按 Electron 的 `NODE_MODULE_VERSION 143` 编译，而 Vitest 使用的 Node.js 需要 `NODE_MODULE_VERSION 137`。
- 打包资源暂存目录没有写权限。
- 专家包测试需要写入受限用户目录。

## 10. 风险与回滚

### 10.1 风险

- 供应方可能发送多段交错的思考与正文事件；生命周期支持重新打开，但仍需使用实际模型覆盖该场景。
- 供应方完全不发送思考结束事件时，只能在消息结束、停止或错误边界兜底完成。
- 本次不改变最终回答判定，如果最终回答事件本身缺失，仍会沿用现有中间回答展示行为。

### 10.2 回滚

代码修复集中在单个提交中，可以整体回滚。回滚后不会影响数据库结构，但会恢复正文流式期间摘要持续显示“正在思考”的旧行为。
