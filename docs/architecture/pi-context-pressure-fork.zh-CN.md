# Pi 上下文压力修复

## 来源与接入

维护 fork：[hawkli-1994/pi](https://github.com/hawkli-1994/pi)，分支 `codex/context-pressure-recovery`，基线为上游 `v1.5.2`（`b4afdddf44e059c67ccf5097e5317d913521b470`）。首轮修复固定为提交 [`9626bbd42749243fad63bef7fbe04154bac294b9`](https://github.com/hawkli-1994/pi/commit/9626bbd42749243fad63bef7fbe04154bac294b9)。旧会话恢复的后续修复位于 `codex/restore-oversized-sessions` 工作分支，并通过应用的 `003+oversized-resume.patch` 自包含接入，详见下文。

应用的 Pi 依赖从 1.4.0 升到 1.5.2；原生源码修复经现有 `patch-package` 安装机制进入 `pi-ai` 和 `pi-coding-agent`。这是一项安装时的依赖补丁，运行时仍由 Pi 自己负责压缩、重试和任务循环。补丁同时保留原有的空 content 容错和本地提供方 overflow 错误识别。

## 确定性故障链

1. Pi 用提供方 usage 判断超过压缩阈值，却用 `字符数 / 4` 决定保留哪些历史。中文上下文的实际计数达到约 63K 时，字符估算可能仍低于默认的 20K 保留预算，导致没有可摘要前缀。
2. 自动压缩原来把“无法准备摘要”静默返回为 `false`，与“压缩成功但不需要续跑”混在一起。后续请求仍携带原上下文。
3. 发送层扣除安全余量后没有输出空间，仍把 `max_tokens` 钳制到 1，制造连续 `length`。
4. 恢复路径先持久化删除截断响应的 context edit，随后才尝试摘要。这会提前失效最新 usage；即使摘要失败，历史和恢复次数也已经改变。
5. 压缩后保留的旧 assistant usage 仍可进入发送层的预算估算。相同毫秒内的压缩和消息使时间戳判断不可靠，可能压缩成功后仍再次得到 1-token 请求。

这些缺陷主要位于 Pi 的压缩准备、会话投影和提供方预算层。这些层负责会话历史与网络协议，必须存在；应修正它们共享的状态与计数规则，而不是在应用外围再建立一个执行循环。

## 修复后的职责

- 压缩切分用真实 usage 校准历史大小的估算。自动压缩确有必要时，保留预算不能阻止选择已有的安全切分点，工具调用与结果仍保持配对。
- 摘要规划在临时投影中运行。摘要成功后才提交 omission 和 compaction；失败或取消保留原历史、usage 和恢复机会。
- 原生自动压缩明确区分成功、失败与取消。请求前压缩失败不会静默发送相同的过满上下文。
- 会话投影按持久化顺序失效压缩/编辑前的 usage；原始消息仍保留计费和诊断信息。
- 输出预算耗尽时产生可识别的原生 overflow，不强行发出 1-token 请求。用户明确请求 1 token 且上下文足够时仍被尊重。
- 小窗口模型的默认保留量与预留量由 Pi 在读取设置时计算。显式设置和模型覆盖仍优先；模型切换、重载与子任务不再依赖应用重复写入预算。

应用也有责任：本次移除启动、继续、队列和子任务路径重复覆盖压缩参数的代码及失效字段；保留已有的截断终态检查，禁止未恢复的 `length` 被标成完成。升级同时将伴随助手的 TypeBox 导入改到实际提供该 API 的 `typebox` 包。

Fork 的 `context-pressure.test.ts` 另外验证内存/持久化会话、连续多次阈值压缩、length 恢复、摘要失败后继续、取消后继续；设置和输出预算测试验证小模型切换及合法的 1-token 请求。现有原生工具配对、排队续跑和扩展压缩回归一并运行。

## 2026-11-12 真实端点 256K 复测

已确认提供方窗口为 262,144 tokens：服务端对 270,015-token 探测明确返回可用窗口 262,144。测试目录按该值解析模型，原生配置为 enabled=true、reserveTokens=16,384、keepRecentTokens=20,000，阈值为 245,760。

用真实模型 `glm-5.3-flash` 对 48 篇合成技术文档执行顺序读取、逐篇摘要、索引和综合报告任务。每篇约 9,000 字符，包含独有校验码和 P99 指标。执行使用完整应用适配器、真实 HTTP/SSE、文件工具、SQLite 和原生 JSONL；Electron 使用测试替身，产物 Worker 通过真实处理函数直接执行，不等同于桌面窗口或安装包验证。没有录制回放，也没有在外围续跑或手工触发压缩。

工作台原始状态为 `needs_review`，验证结果为 `acceptance_required`，原因是该独立适配器夹具未挂载产品的产物验证工作流，三个声明交付物按既有策略等待验收。基线完整性、最终回复和流关闭检查均通过。这与执行未完成却伪报成功不同；本轮另对文件内容、原生会话和传输记录做了独立复核。没有改写原始数据库来伪造已验收状态。

本轮主测试和证据复核通过，未复现阈值不压缩、连续 length 中止、缺少产物却完成的问题。一次网络读取超时已由原生机制恢复，不能把本轮描述为“所有传输请求均无异常”。这是一轮 256K 实测，不代表所有模型、窗口或负载都已覆盖。

## 2026-11-12 已超限旧会话的恢复修复

此前 256K 新任务通过，不代表已经积累到 40 万 token 以上的旧会话可以恢复。代码中仍有两个缺口：原生摘要把整个待压缩前缀交给单次模型请求，摘要请求本身就超过窗口；恢复前检查又把压缩失败降为“不需要继续”，随后仍尝试发送原上下文。物理模型的首个请求还缺少新输入进入投影后的阈值检查。

第三段依赖补丁在 Pi 内部修复这些问题：

- 摘要与轮次前缀摘要共用有预算约束的分块归并。预算复用发送层的估算与安全余量，至少保留 `min(model.maxTokens, 4096)` 的输出空间；服务端计数更高而拒绝上下文时继续细分。全部源文本参与摘要，不直接丢弃前缀。
- 每个中间摘要都必须完整结束、有正文且不调用工具。失败、截断、取消或摘要无法缩短时停止；全部摘要成功后才提交原生 compaction/context edit，失败保留原始消息与恢复机会。
- 恢复前压缩失败向调用者传递原因，不再继续发送相同超限输入；实际首个请求也检查新提示和工具配置进入后的投影。一次请求准备失败不再触发同一轮重复摘要。
- 连续截断仍限制自动恢复次数。用户明确发起新一轮时，在恢复前检查之前重置恢复次数，避免上一轮失败永久挡住“继续”。

应用外围只负责投影：记录压缩开始、结束、取消及失败原因；需要恢复的未完成响应保留失败原因到终态，成功续跑可以清除它。已正常完成回复之后的摘要维护失败只记录诊断，不改判已完成工作。JSONL 恢复日志在真正打开会话后记录消息数、模型与上下文窗口，移除此前伪造的三个零值；不扫描、复制或记录历史正文。

`piOversizedResume.test.ts` 使用本地 HTTP/SSE 提供方、完整应用适配器和真实 SQLite/JSONL，构造超过 40 万估算 token 的历史。测试服务按实际请求文本计算窗口占用并拒绝超限请求，覆盖 64K/256K、旧 overflow、旧 length、摘要中途截断后重新恢复，以及关闭后再次恢复。验收包括全部 48 个有序证据标记确实写入文件、完成事件准确、失败时没有产物或 compaction/context edit、原始消息保留、已完成工具不重复执行。该测试不使用磁带，也不读取本机用户会话或调用真实模型端点。

对照验证：只换回修复前的 Pi 实现，新增的 5 个恢复用例全部失败，并复现摘要自身超限后继续发送原上下文的错误链；恢复补丁后 5 项全部通过。

本轮本地验证：应用相关单测 570 项及原生 SDK 集成 2 项通过；Pi 相关回归 132 项通过、15 项依赖其他条件的用例跳过。应用构建、Electron 类型检查、依赖补丁安装、Knip、格式和源码行数检查通过；lint 命令通过，改动文件没有警告，全仓仍有未改动文件的存量警告。Pi coding-agent 包、示例类型检查及全仓 Biome 通过；Pi monorepo 全量类型检查仍被未安装的工作区开发依赖阻塞，不能标为通过。离线协议与状态回归不等同于真实模型摘要质量、用户原会话或 Windows 安装包复测。

## 边界

这次修复不承诺无限恢复。没有安全可压缩历史、提供方拒绝摘要、用户取消、或一次原生恢复后仍连续截断时，必须保留诊断并明确结束为失败/取消，不能伪装完成。超大的不可压缩系统提示、工具定义或单条工具结果仍需要单独处理其来源。
