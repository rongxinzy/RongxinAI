# Python Runtime

Workspace-isolated Python execution, package management and Skill execution for 知远智能体 (ZhiYuan Agent).

## Runtime and environment versions

The host supplies absolute paths to the bundled CPython/uv pair and the preinstalled dependency baseline at `resources/skill-python/layers/shared`. The application does not download an interpreter during a task. A build missing these resources rejects Python operations with a reinstall hint. The baseline includes the office/PDF core, so a new workspace can import pandas, numpy, openpyxl, matplotlib, reportlab, pypdf, pypdfium2 and Pillow without installing packages from the network.

Workspace state lives under `userData/python-runtime/workspaces-v2/<sha256(real-workspace-path)>/`. Workspace symlink aliases share one identity. Each workspace has independent versioned venvs and a `current.json` containing the runtime ID, baseline manifest fingerprint, environment ID, frozen package versions and verified Skill lock fingerprints. On Windows, new venvs use `userData/python-runtime/venvs/<uuid>/` to leave room for DLL paths. The next Python operation copies an existing long-path venv's packages into a short-path candidate and switches `current.json` after validation. The former `workspaces/` layout is left untouched and is not loaded.

A new workspace creates a venv and seeds it from the preinstalled baseline. Subsequent installs seed a fresh candidate from the current workspace environment. Package directories use copy-on-write clones where supported, with ordinary copying as the fallback; they are never hard-linked to the shared baseline or another workspace. ABI checks precede copying. Package resolution, `uv pip check` and freezing must all succeed before `current.json` switches atomically. Failure or cancellation removes the candidate and preserves the active environment. Old successful environments remain on disk. On POSIX, copied Python console scripts are rebound to the candidate interpreter. Windows copies wheel-owned executables, updates uv launchers to use the candidate interpreter, recreates remaining console entry points as `.cmd` / `-script.py`, and supplies a workspace-local `python3.exe` alias.

An explicit `rebuild: true` seeds a new environment from the packaged baseline and restores the frozen requirements. It checks installed versions first and installs only missing or mismatched packages, then verifies the complete lock instead of resolving the already satisfied baseline again. A runtime ID or baseline fingerprint change requires this explicit rebuild; startup does not silently upgrade an existing environment. The runtime ID (`bundled-cpython-<py>-uv-<uv>` from `bundledRuntime.ts`) tracks the packaged interpreter and uv pair. The host resolves the interpreter, uv and dependency baseline together from one installer-owned resource root; older user-data copies cannot shadow them.

## Packages and Skill dependencies

`python_install` accepts registry package names, extras and common version constraints, including `packaging`, `requests[socks]>=2.31,<3`, exact pins and `==1.*`. The installer resolves names/ranges and records exact frozen versions, so the model does not need to guess a version. URLs, VCS/local paths, environment markers and command-line flags are rejected. Model requests are limited to 40 requirements of 200 characters each; the host-generated frozen package closure has a separate larger bound.

Installation remains **wheel-only**. A package must publish a wheel compatible with the bundled Python and target platform; a source-only distribution or incompatible native wheel fails without attempting a compiler build. The integration matrix covers an unpinned/ranged pure-Python install and a real NumPy array calculation on the pinned interpreter. Additional native extensions and platforms need their own compatibility evidence.

All workspace and Skill dependency installs use the same `runtimeNetworkEnvironment` and shared uv cache. These installs use official PyPI by default and honor host-provided `UV_INDEX` and `UV_DEFAULT_INDEX`. The tools do not accept index flags from the model. Proxy and CA environment variables reach uv; application credentials and external Python path overrides do not.

`run_skill_script` routes Python scripts through the same `PythonRuntimeService` and workspace interpreter as `python_execute`. Shell wrappers and long-lived Skill processes prepare that workspace environment first. Skill requirement files are fingerprinted against their packaged `skills/<skillId>/runtime.json` before dependency work. Version 3 overlay manifests additionally identify a SHA-256-verified lock inside `skill-python/locks`; the Runner installs an immutable snapshot with `--require-hashes --no-deps`. Large dependency downloads require the existing `confirmDependencyInstall` decision. A missing/stale manifest or mismatched lock fails closed; there is no `uv run --with-requirements` fallback. Verified version 2 full-core manifests use the packaged baseline without a delta lock.

## Invocation and lifecycle

`PythonRuntimeService({storageRoot, runnerPath, jobRunnerPath?, preinstalledRuntime?, uvCacheDir?})` exposes `execute`, `install`, `prepare` and `shutdown`; `host.ts` resolves the bundled interpreter, uv and shared baseline into `preinstalledRuntime`. At most two workspaces run concurrently, each canonical workspace is serialized, and up to 64 operations can wait. Cancelling a queued request removes it immediately; shutdown rejects queued and future work. `prepare` returns the ready workspace interpreter for a host-owned Skill process. Each operation forks the bundled `runner.ts` entry using `ELECTRON_RUN_AS_NODE=1`; scanning/copying the baseline, manifest/hash checks, package resolution and Python execution stay outside the main process.

`buildPiPythonTools({service, workspace})` exposes the product interfaces `python.execute` and `python.install` as native Pi tools named `python_execute` and `python_install`. OpenAI/Anthropic function names reject dots, and Pi transmits tool names verbatim; the underscore wire names keep these interfaces portable. Pi authorization runs before the Runner starts. The model supplies Python source or package requirements against the host-bound workspace; Skill paths, requirements files and runtime locations are supplied by the host. This is local code execution with the user's filesystem permissions, not a filesystem sandbox.

The Runner launches executables directly with `shell:false`. Script cwd is the workspace. stdout/stderr are capped together at 1 MiB; results report truncation and the real exit code. Execution timeout defaults to 60 seconds; install and Skill dependency operations default to five minutes unless the caller supplies a timeout. The Runner caps standalone operations at ten minutes and host-owned Skill operations at fifteen minutes. Cancellation and application shutdown terminate active work. Workspace Python owns `VIRTUAL_ENV`, Python executable variables and its PATH entry; host-owned Skill locations and selected network settings cross an explicit allowlist.

On Linux/macOS a small independent supervisor owns each subprocess group. It watches the Runner IPC connection and kills the group on Runner death, including SIGKILL, as well as on completion/cancellation. The supervisor reuses the bundled Runner entry and needs no system shell or additional dependency. On Windows, `job-runner.exe` creates the child within a Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The helper also waits on the Runner process handle. Missing helper, process launch failure or missing parent fails closed.

## Build and tests

Bundle `src/main/pythonRuntime/runner.ts` as a separate CommonJS entry named `dist-electron/python-runtime-runner.js`. On Windows compile `scripts/python-runtime/job-runner.cpp` using `build-job-runner.ps1` in the MSVC developer environment and package `resources/python-runtime/job-runner.exe` as an unpacked resource.

Unit/native authorization tests: `bunx vitest run src/main/pythonRuntime src/main/libs/agentEngine/piPythonTools.test.ts`.

Provision the real baseline before integration tests. On macOS/Linux run `bun run setup:posix-python-runtime`, `bun run setup:posix-uv-runtime` and `bun run setup:skill-python-runtime`. On Windows use `bun run setup:python-runtime`, `bun run setup:uv-runtime` and `bun run setup:skill-python-runtime`. The Skill setup also validates the base runtime, core imports and per-Skill manifests, including when restored from cache.

Build the Runner, set `PYTHON_RUNTIME_INTEGRATION=1` and `PYTHON_RUNTIME_RUNNER` to its output, then run `runtime.integration.test.ts` and `skill.integration.test.ts`. Tests use the provisioned `resources/` paths; explicit test-only overrides are `PYTHON_RUNTIME_BUNDLED_PYTHON`, `PYTHON_RUNTIME_BUNDLED_UV` and `PYTHON_RUNTIME_BUNDLED_SHARED_PYTHON`. Windows tests additionally set `PYTHON_RUNTIME_JOB_HELPER`. Coverage includes offline core imports, independent workspace package files, install/rebuild failure preservation and process cancellation. The real XLSX script reads a pandas-generated workbook through its verified Skill manifest and workspace interpreter. A version 3 delta fixture installs a real small wheel with published artifact hashes, exercises confirmation before download and reuse without repeated confirmation, shares that package with native Python execution, and rejects a subsequently modified lock. Synthetic large-package metadata exercises the download decision without claiming compatibility coverage for an actual large dependency.

`.github/workflows/python-runtime.yml` provisions this baseline for manual Linux/Windows checks and exercises the real Windows helper, including child/grandchild cancellation, parent-death cleanup and Unicode/quoted argv. The Python job in `release-preflight.yml` supplies the same Linux baseline. Their Skill resource caches include the setup implementation, bundled runtime version and every Skill requirement fingerprint in the key; setup verification still runs after cache restoration. These checks do not require signing or install into a user's Python environment.
